# SEP — архитектура MVP

Статус: **утверждённое архитектурное решение для первой реализации**.

Математическая модель и инженерные ограничения остаются в [`specification.md`](./specification.md). Этот документ описывает только структуру приложения, технологический стек и правила взаимодействия модулей.

## 1. Основной принцип

SEP v1 реализуется как полностью клиентское приложение без серверного backend.

Расчётное ядро является отдельной TypeScript-библиотекой и не зависит от React, Vite, браузерного DOM, HTTP, базы данных или конкретного способа отображения результатов.

Клиентское приложение импортирует расчётное ядро как workspace-пакет и выполняет вычисления локально в браузере.

```text
Пользователь
    ↓
Vite + React client
    ↓
@sep/core
    ↓
расчёты / ограничения / Pareto
    ↓
Solution[]
    ↓
таблица + фильтры + 3D-график
```

## 2. Технологический стек

### Монорепозиторий

- Turborepo;
- package manager: `pnpm` workspaces;
- TypeScript во всех пакетах и приложениях.

### Расчётное ядро

- TypeScript;
- пакет `@sep/core`;
- Vitest для unit/regression tests;
- расчётные функции должны быть детерминированными и по возможности pure functions;
- библиотека не должна зависеть от React/Vite.

### Клиентское приложение

- Vite;
- React;
- TypeScript;
- приложение `apps/web`;
- расчёты выполняются в браузере через `@sep/core`;
- серверное приложение в MVP отсутствует.

Для UI позже могут быть подключены отдельные библиотеки таблиц и визуализации. Конкретный выбор не должен влиять на API расчётного ядра.

### CI/CD

GitHub Actions.

На pull request и push должны выполняться:

1. установка зависимостей;
2. lint;
3. TypeScript typecheck;
4. unit/regression tests;
5. production build клиента.

Для статического MVP рекомендуется deploy собранного Vite-приложения в GitHub Pages после успешного pipeline в `main`.

## 4. Ответственность `@sep/core`

Пакет должен содержать всю предметную и математическую логику SEP.

Минимальные модули:

### `cosine`

Расчёт среднего `cos(alpha)` по утверждённой двухэтапной интерполяции.

Пример публичного API:

```ts
calculateAverageCosine({
  altitudeKm: 1200,
  concentration: 2,
}): number
```

### `power`

Расчёт мощности одной конфигурации.

### `mass`

Расчёт массы конструкции и концентратора.

### `constraints`

Проверка инженерных ограничений.

### `generator`

Полный перебор конфигураций и формирование списка допустимых решений.

### `pareto`

Определение недоминируемых решений и установка `isPareto`.

### `models`

TypeScript-типы входных данных, справочников и результатов.

## 5. Требования к расчётному ядру

`@sep/core` не должен:

- импортировать React;
- использовать DOM API;
- выполнять HTTP-запросы;
- читать файлы напрямую;
- зависеть от localStorage;
- хранить UI state;
- знать о Plotly, таблицах или форме ввода;
- разбирать CSV или зависеть от File API / CSV-библиотек.

Импорт таблицы ФЭП из CSV выполняется только в `apps/web`: файл читается в браузере, разбор и валидация не переносятся в `@sep/core`. Порядок «Парето сверху» — presentation sorting клиента, а не изменение алгоритма `markParetoSolutions`.

Расчётные функции получают данные аргументами и возвращают результат.

Пример верхнеуровневого API:

```ts
const result = calculateSep({
  altitudeKm: 1200,
  maxMassKg: 100,
  requiredPowerW: 2500,
  maxPanelAreaM2: 5,
  panelCount: 2,
  photovoltaicCells,
  structures,
  concentratorMaterials,
});
```

Результат:

```ts
interface SepCalculationResult {
  solutions: SepSolution[];
  totalGenerated: number;
  totalFeasible: number;
}
```

## 6. Тестирование

Тесты математического ядра размещаются рядом с `@sep/core` и запускаются через Vitest.

Обязательные категории:

1. regression tests для всех 35 опорных значений `cos(alpha)`;
2. тесты промежуточных `H` и `K`;
3. тесты мощности;
4. тесты массы;
5. тесты ограничений;
6. тесты генератора конфигураций;
7. тесты Pareto;
8. тесты ошибок и граничных значений.

UI-тесты не заменяют unit tests математической библиотеки.

Расчётное ядро считается источником истины, поэтому изменение математических результатов должно приводить к падению regression tests.

## 7. Turborepo tasks

Минимальный набор задач:

```text
build
test
lint
typecheck
dev
```

Пример логики pipeline:

```text
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

Turborepo должен запускать соответствующие команды только для пакетов, которым они требуются, и использовать cache там, где это безопасно.

## 8. GitHub Actions CI

Workflow `ci.yml` запускается минимум на:

```text
pull_request
push -> main
```

Pipeline считается успешным только если прошли:

```text
install
  ↓
lint
  ↓
typecheck
  ↓
test
  ↓
build
```

Рекомендуемая версия Node.js должна быть зафиксирована в репозитории, а lockfile — закоммичен.

## 9. GitHub Actions CD

Так как приложение полностью статическое, отдельный application server не требуется.

Для MVP рекомендуемый deployment:

```text
main
 ↓
CI успешно
 ↓
Vite production build
 ↓
GitHub Pages
```

`deploy.yml` не должен публиковать новую версию, если тесты или build завершились ошибкой.

Если позднее будет выбран другой статический hosting, это не должно потребовать изменений в `@sep/core`.

## 10. Что сознательно отсутствует

На первой итерации не создаём:

- NestJS/Fastify/Express backend;
- REST/GraphQL API;
- базу данных;
- авторизацию;
- серверное хранение расчётов;
- Docker-инфраструктуру только ради запуска приложения.

Если в будущем появится необходимость хранить проекты, делиться расчётами или выполнять тяжёлую серверную математику, backend добавляется отдельным приложением в `apps/`, не меняя публичный контракт `@sep/core`.

## 11. Порядок реализации

1. создать Turborepo workspace;
2. настроить общие TypeScript-конфиги;
3. создать `@sep/core`;
4. подключить Vitest;
5. создать минимальный Vite + React client;
6. настроить импорт `@sep/core` из клиента;
7. настроить `lint`, `typecheck`, `test`, `build` через Turbo;
8. добавить GitHub Actions CI;
9. добавить статический deploy;
10. после этого переходить к реализации математических модулей по отдельным issues.

## 12. Критерий готовности архитектурного этапа

Архитектурный bootstrap считается завершённым, если:

- `pnpm install` работает с чистого checkout;
- `pnpm dev` запускает Vite-приложение;
- клиент успешно импортирует функцию из `@sep/core`;
- `pnpm test` запускает тесты библиотеки;
- `pnpm typecheck` проходит для всего workspace;
- `pnpm build` собирает весь монорепозиторий;
- CI выполняет эти проверки на PR;
- приложение может быть опубликовано как статический build без backend.
